# PRD — Making the Vault Retrievable

**Date:** 2026-09-01
**Status:** draft, awaiting approval. No code changes made.
**Scope:** the **Now** and **Next** columns of `2026-09-01-strategy.md`. Strategy + UX only; the visual system in `DESIGN.md` is unchanged.

---

## 1. Executive summary

Reel Vault has captured 198 items across three years and made none of them findable: 0% carry a summary, 53% have no usable title, and the two available filters restate a field the user already knows. Search and chat rank over columns that are empty for every row. The cause is architectural — description is a manual step behind a button that only appears after a sync, and it has never run.

This PRD makes description a property of ingest rather than a user action, backfills the existing corpus, and tells the user the truth about coverage and staleness. It deliberately does **not** reorganise the information architecture yet, because reorganising undescribed content is rearranging the hoard.

---

## 2. Problem statement

See `2026-09-01-strategy.md` §2. In one line:

> Reel Vault has captured three years of content and made none of it findable, because description is an optional step the user must trigger.

**Evidence:** 0/198 summaries, 0/198 notes, 104/198 generic titles, 2 categories both derived from `origin`, 85 days since last sync, enrichment reachable only via a post-sync button processing 20 items per press.

---

## 3. Target user & job

One person: the owner. Full JTBD in `2026-09-01-strategy.md` §1.

**Primary job:** *"When I half-remember something I saw months ago, help me get it back in seconds without opening Instagram."*

**Secondary job:** re-read a DM thread and recover the reels traded inside it.

**Explicit non-job:** taking notes. Used on 0 of 198 items over three years. Notes stay, but nothing in this PRD is built around them.

---

## 4. Strategic context

**Goal:** raise successful retrieval from near-0% to ≥80% (8/10 deliberate searches, ≤30s each, no Instagram).
**Leading indicator:** enriched coverage, currently 0%.

**Why now:** every other part of the product works. Ingest is solid (198 items, 192 messages, correctly deduped, original timestamps preserved), thumbnails are 100% populated, the visual system is coherent. The one missing layer is the one the product exists for.

**Competitive frame:** the alternative is Instagram's Saved tab. On today's data Reel Vault is *not better than it* — same unsearchable grid, plus a sync step. Coverage is what creates the difference.

---

## 5. Solution overview

Four changes, in dependency order.

### 5.1 Backfill worker *(the POC — everything else is gated on it)*

A resumable job that enriches every item lacking a summary, without the user pressing anything ten times.

- Runs until the pending queue is empty, not 20-at-a-time.
- Survives interruption; re-running resumes rather than restarting.
- Reports progress and a final count.
- Degrades explicitly: when the sidecar is down, enrich from title alone and **record that the item was enriched in degraded mode** so quality can be audited later.

### 5.2 Disclosure before egress *(ships before 5.1 runs — the one hard ordering constraint)*

A one-time consent step naming the provider, what is sent, and how much. Enrichment is blocked until it is accepted.

Non-negotiable because the backfill's first act is to send three years of private DM content to a third party, under a UI that currently says "Local first · Private · Yours".

### 5.3 Enrichment at ingest

Once 5.1 proves description quality, `storeGathered()` enqueues each new item for enrichment. The manual button disappears. Coverage stays at 100% with no user action.

### 5.4 Honest state in the UI

The dashboard states, in the existing quiet meta register:

> `198 kept · 100% described · synced 85 days ago`

Currently the app presents a 0%-described, 85-day-stale vault as if it were complete. Staleness becomes an affordance to sync rather than a silent fact.

## 6. Success metrics

| Metric | Current | Target | How measured |
|---|---|---|---|
| **Retrieval rate** (primary) | assumed ~0% | ≥80% | 10 pre-written searches, hit/miss recorded |
| Time to find | unbounded | ≤30s median | stopwatch, same 10 searches |
| Enriched coverage | 0% | 100% | `select count(*) from items where summary is not null` |
| Description quality | n/a | ≥16/20 | manual inspection of 20 random summaries |
| Manual steps to full coverage | 10 presses | 0 | — |

**Quality gate:** if description quality fails 16/20, stop. The problem is enrichment quality, not IA, and the next branch is vision-from-thumbnail (strategy §4, solution 1.3) — not any of the layout work.

## 7. Requirements

### R1 — Backfill worker
- **R1.1** Process all items with `summary is null`, not a fixed page of 20.
- **R1.2** Resumable: interrupting and re-running continues from where it stopped.
- **R1.3** Reports `{enriched, failed, remaining}`.
- **R1.4** A per-item failure is logged and skipped, never fatal to the run.
- **R1.5** Records whether each item was enriched with sidecar content or from title alone.
- **AC:** given 198 unenriched items, one invocation with the sidecar up ends with 0 remaining and a per-item mode recorded.

### R2 — Disclosure
- **R2.1** Names the provider, the fields sent, and the item count.
- **R2.2** Enrichment is blocked until accepted; the decision persists.
- **R2.3** Reachable and revocable afterwards.
- **AC:** a fresh vault cannot send a single item to Groq before acceptance.

### R3 — Enrichment at ingest
- **R3.1** `storeGathered()` enqueues new items for enrichment.
- **R3.2** Enrichment failure never blocks or rolls back ingest.
- **R3.3** No user action required for a synced item to become described.
- **AC:** after a sync of N new items, coverage returns to 100% with no button pressed.

### R4 — Honest state
- **R4.1** Dashboard shows item count, coverage %, and sync age.
- **R4.2** Coverage below 100% offers the backfill directly.
- **R4.3** Sync age over 7 days is visually marked stale and links to `/connect`.
- **AC:** today's vault reads `198 kept · 0% described · synced 85 days ago` before backfill, `100%` after.

### R5 — Documentation truth *(cleanup, no user-facing change)*
- **R5.1** `CLAUDE.md` states Groq `llama-3.3-70b-versatile` via `GROQ_API_KEY`, not Anthropic.
- **R5.2** Remove the unused `@anthropic-ai/sdk` dependency.
- **R5.3** Apply the `PRODUCT.md` replacement from strategy §6.

### Edge cases
- Sidecar down → degraded enrichment, flagged, not a failure.
- Groq rate-limited or key absent → pause and report, never a partial write.
- Generic-titled item with no sidecar content → will produce a weak summary; this is exactly what the 16/20 gate is for.
- Backfill launched twice → second run finds an empty queue and exits.

## 8. Out of scope

| Notes improvements | Zero usage in three years. |
| Deleting `/messages` | Its 95%-of-corpus status makes it a candidate for *promotion*, not deletion — decide after the experiment. |

## 9. Dependencies & risks

| Risk | Mitigation |
|---|---|
| Backfill sends 3 years of private DMs to Groq | R2 ships first. Hard ordering constraint. |
| Description quality too low to retrieve on | 16/20 gate before any downstream work; vision path held in reserve. |
| Sidecar must run for good descriptions | Degraded mode is explicit and recorded (R1.5), not silent. |
| Sync throttles (20h / 6h) slow validation of R3 | Validate R3 on one small sync; R1 needs no sync at all. |
| Groq cost/rate limits on a 198-item burst | Resumable by design (R1.2). |
| **Conclusion may be that reels are not retrievable from text** | The experiment is designed to surface this in a week. A real possible outcome. |

## 10. Open questions

Blocking — from audit §5:

1. Is the DM thread the product, or did the saved-posts sync fail? Changes whether IA work is promotion or repair.
2. Why did enrichment never run — unknown button, sidecar down, or silent failure? If it was tried and failed, R1 is a bug fix, not a feature.
3. What did you last fail to find? The only real evidence of the retrieval job, and the source for the ten test searches.
4. Is disclosed third-party enrichment acceptable, or is local-only required?
5. Does 85 days stale bother you? Determines whether sync automation ever enters the roadmap.

Non-blocking: should degraded-mode items be re-enriched automatically once the sidecar returns? Should coverage be per-origin?
